## 4. API 2 — Bill Payment

`POST https://app.fintap.pk/api/1.0/Payments/BillPayment`

Required headers are the same as Bill Inquiry.

Example request for the unpaid PKR 4,999 fixture:

```json
{
  "consumer_number": "10517210010002",
  "tran_auth_id": "<unique 6-digit value>",
  "transaction_amount": "000000499900",
  "tran_date": "<YYYYMMDD>",
  "tran_time": "<HHMMSS>",
  "bank_mnemonic": "MBLINK01",
  "reserved": ""
}
```

Expected successful response:

```json
{
  "response_Code": "00",
  "Identification_parameter": "UAT Slab 1B",
  "reserved": ""
}
```

`transaction_amount` is exactly 12 numeric characters with the last two digits representing paisa. Bill Payment is state-changing: use a unique six-digit authorization ID and submit each intended success case once. A live success call was deliberately not consumed during preparation so 1LINK can execute it during UAT.

## 7. Response-code clarification required from 1LINK

The supplied Generic REST v1.5 document is the controlling technical contract for the implemented endpoints. It defines inquiry codes `00`–`05`, plus summary code `06` for an already-paid bill; payment codes include `00`–`06` with endpoint-specific meanings.

The supplied test-case workbook also contains ISO-style values such as `89`, `91`, `92`, and `94`, while its disclaimer points back to the technical specification. Before formal execution, 1LINK should confirm that the Generic REST codes are expected for these two REST endpoints.

The Generic REST document also contains an internal inconsistency: its field definition allows up to 24 characters but separately states that 1LINK's maximum is 20. The kickoff requirement explicitly asks for one 24-digit test consumer, which is included above. 1LINK must confirm that its UAT gateway will not reject that case before forwarding it.
